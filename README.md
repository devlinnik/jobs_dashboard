# Devlin Desk

Локальное приложение для Windows: проекты, мониторинг сайтов, SSH, свободное место на серверах, Git и уведомления Telegram. Интерфейс на русском языке, работает в отдельном окне. Python + FastAPI + pywebview; данные — SQLite, интерфейс — HTML/CSS/JS без внешних CDN.

## Установка на Windows — двойным щелчком

Скачайте или клонируйте репозиторий в папку, доступную для записи, и запустите **`DevlinLauncher.exe` → «Установить»** в корне. Нужны Windows 10/11 x64, интернет для первой установки/обновления и несколько гигабайт свободного места для среды сборки. Git не обязателен при установке из ZIP.

Готовый лаунчер включён в репозиторий. Он работает на .NET Framework 4.8 (обычно установлен в Windows 10/11), открывается без Python и показывает stdout/stderr установщика в реальном времени. Доступны выбор папок, установка, обновление, локальная сборка, создание ярлыка и открытие приложения. Весь журнал автоматически сохраняется в `%LOCALAPPDATA%\DevlinDeskLauncher\logs`; кнопка «Сохранить журнал» позволяет выбрать другой файл. Если установка завершилась с ошибкой, журнал остаётся видимым и можно повторить операцию.

Во время установки закрытие лаунчера блокируется, чтобы не прерывать замену файлов. Лаунчер запускает временную копию самого себя: EXE в корне или `dist` освобождается перед обновлением. Исходники лаунчера — `scripts/DevlinLauncher.cs`; воспроизводимая сборка на Windows: `powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/build-launcher.ps1`. После изменения встроенных скриптов пересоберите лаунчер этой командой; Тесты проверяют актуальность встроенных скриптов, CI пересобирает EXE из C#-исходника и проверяет нативный запуск.

Лаунчер можно запускать из `dist` даже после удаления исходников; в этом случае он скачает текущую версию из GitHub. Если изначально запускается только EXE вне репозитория, установщик сохраняет сборку в `%LOCALAPPDATA%\DevlinDeskUpdater\dist\DevlinDesk`.

Установщик:

1. Проверит Python 3.12 x64; при отсутствии скачает официальный установщик Python 3.12.10 с `python.org` и установит для текущего пользователя.
2. Проверит Microsoft Edge WebView2 Runtime; при отсутствии установит официальный Evergreen Runtime Microsoft. Windows может запросить подтверждение или перезагрузку.
3. **До запуска скачанных установщиков проверит Authenticode-подпись и точное имя издателя**: Python Software Foundation либо Microsoft Corporation. Ошибка подписи останавливает установку; проверка TLS не отключается.
4. Создаст отдельную среду `.build-venv` и соберёт приложение через PyInstaller во временной папке `.build`.
5. Проверит автономный лаунчер (ресурсы, запуск PowerShell, вывод и код завершения), затем запустит новую сборку в режиме `--self-test`: проверка локального API, HTML, JS и CSS, без окна и без пользовательских данных.
6. Разместит проверенную сборку в **`dist\DevlinDesk`** и создаст ярлык **Devlin Desk** на рабочем столе текущего пользователя.

В результате:

```text
jobs_dashboard/
  DevlinLauncher.exe        окно установки, обновления и журнала
  Start-Devlin.cmd           запуск установленного приложения
  dist/                     не попадает в Git
    DevlinDesk/
      DevlinDesk.exe
      DevlinLauncher.exe    окно обновления прямо из папки приложения
      README.txt            краткая инструкция
      runtime/              библиотеки, интерфейс и иконка
      maintenance/          автономные файлы обновления
        install-info.json   версия сборки и путь к исходникам
    backups/                предыдущие версии после обновлений
      DevlinDesk-ДАТА-ИД/
```

**`Start-Devlin.cmd` в корне** открывает установленное приложение; если сборки ещё нет, открывает лаунчер. В лаунчере нажмите «Установить», дождитесь успешного результата и нажмите «Открыть приложение». Можно также открыть ярлык на рабочем столе.

Лаунчер запускает PowerShell с `ExecutionPolicy Bypass` **только для этого процесса**. Политика пользователя/компьютера не меняется. Корпоративная Group Policy может запрещать выполнение даже в этом режиме; в таком случае разрешение должен дать администратор, скрипт его не обходит. Если ярлык не удалось создать, установка остаётся успешной и показывает путь к `.exe`.

Приложение слушает только 127.0.0.1 и выбирает свободный порт. В Windows **крестик скрывает окно в системный трей**: проверки проектов и уведомления Telegram продолжают работать. Щелчок по значку открывает окно; правая кнопка показывает меню со статусами проектов и пунктом **«Выход — остановить мониторинг»**. Значок может находиться под стрелкой скрытых значков Windows. При первом скрытии появляется уведомление.

Меню использует результаты последних проверок, не запускает дополнительные SSH/Git-команды. Статусы и подсказка обновляются каждые 10 секунд; если включён PIN, сведения о проектах скрыты и доступны только в приложении после ввода PIN. Если значок трея недоступен, закрытие окна завершает приложение. Полный выход ожидает завершения активных SSH/Git-операций и сохраняет их результат. В браузерном режиме процесс работает до Ctrl+C. Автозапуск Windows не добавляется.

Иконка EXE, ярлыка, окна и трея — мятная монограмма D с графиком статуса. Исходник PNG и Windows ICO (16–256 px) находятся в `dashboard/assets`. ICO встроен в EXE; в `runtime` лежит копия для окна и трея.

Если после установки Проводник показывает старый значок, запустите **`Refresh-Icons.cmd` в корне исходников** и заново откройте папку приложения (или нажмите F5). Пересборка для этого не нужна. Установщик также автоматически уведомляет Windows об обновлении значков через `SHChangeNotify`, без удаления системного кеша и перезапуска Проводника. Ярлык использует ICO напрямую. Если Windows продолжает показывать старый значок, выйдите из учётной записи и войдите снова, предварительно сохранив открытые документы.

На Windows проверка собранного EXE теперь сравнивает все встроенные ресурсы иконки с исходным ICO, а не только наличие ICO в папке. Несовпадение останавливает установку до замены предыдущей версии. По одному изображению из Проводника нельзя определить, устарел ли кеш или сам ресурс EXE.

## Обновление приложения

Выберите **«Выход — остановить мониторинг» в меню трея**, затем запустите **`DevlinLauncher.exe` → «Обновить»** в корне либо рядом с `.exe` в `dist\DevlinDesk`. Одного закрытия окна теперь недостаточно.

**Первый переход с прежней структуры:** закройте старое приложение, выполните `git pull --ff-only` в исходниках и запустите `DevlinLauncher.exe` → «Установить» из корня. Это обновит сам упаковщик перед пересборкой; старый updater внутри `_maintenance` ещё использует прежние правила упаковки. Последующие обновления запускаются новым `DevlinLauncher.exe` → «Обновить».

Новый updater при изменении сборочного скрипта в полученных исходниках передаёт сборку новой версии упаковщика. Поэтому будущие изменения структуры и ресурсов приложения применяются вместе с кодом.

- В чистом Git-checkout на ветке `main` обновление получает `origin/main` и применяет **только fast-forward**. Разошедшаяся история останавливает обновление; reset/force не выполняются.
- Если есть локальные изменения, Git не установлен либо выбрана другая ветка, ваши исходники сохраняются и **собирается текущая локальная версия**. Сообщение об этом видно в окне установщика.
- Для ZIP-версии или переносимой сборки без исходников обновление скачивает текущий `main` из `devlinnik/jobs_dashboard` через HTTPS в отдельную временную папку. Оригинальная папка исходников не перезаписывается. Адрес репозитория закреплён в коде.
- Если вы дорабатываете ZIP-исходники локально и хотите собрать их вместо версии GitHub, используйте **`DevlinLauncher.exe` → «Установить»** либо «Обновить» с флажком «Обновлять из локальных исходников» из корня. Локальный режим требует сохранённой папки исходников.

Новая версия сначала собирается и проверяется отдельно. До этого текущая сборка не меняется. Запущенное приложение **не завершается принудительно**: обновление попросит его закрыть. Параллельные установки блокируются.

Перед заменой текущая версия переносится в **`dist\backups\DevlinDesk-ДАТА-ИД`**. Эти копии не удаляются автоматически и не перезаписывают предыдущие резервные версии. Если финальная замена не удалась, старая папка возвращается. Время в имени резервной копии — местное время вашего ПК. Существующие копии `DevlinDesk.previous-*` от прежних версий остаются на месте.

Для ручного отката выйдите через трей, сохраните неудачную папку отдельно и перенесите выбранную копию из `backups` в `dist` под именем `DevlinDesk`, чтобы ярлык снова указывал на неё. Резервные сборки можно удалить вручную после проверки новой версии.

**Проекты, PIN, SSH-доступы и токены сохраняются**: установщик не читает и не удаляет `%LOCALAPPDATA%\DevlinDesk`. Он не выполняет миграций рабочей базы при проверке сборки; проверка использует временные данные. Если в будущих версиях изменится схема базы, разработчик должен добавить совместимую миграцию в приложение. Старый бинарник может быть несовместим с новой схемой: перед большим обновлением делайте резервную копию каталога данных.

Обновление из `dist` копирует служебные файлы в TEMP и работает оттуда: Windows не удерживает файлы внутри заменяемой папки. Переносите **всю папку `DevlinDesk`**, включая `runtime` и `maintenance`. Установка поверх предыдущей структуры (`_internal`, `_maintenance`) поддерживается: старая папка целиком сохраняется в `backups`, новая получает новую структуру. Если исходный checkout больше недоступен, updater использует отдельный кеш `%LOCALAPPDATA%\DevlinDeskUpdater` и получает исходники из GitHub. Для запуска готового `.exe` Python не нужен; для самостоятельной пересборки updater установит его при необходимости.

Папки `dist`, `.build`, `.build-venv`, старые сборки и временные файлы обновления исключены из Git. В репозитории хранятся только исходники и воспроизводимые команды сборки.

### Если установка завершилась с `WinError 5` (отказано в доступе)

Успешная сборка EXE ещё не означает завершённую установку: затем установщик копирует файлы, запускает проверку EXE и заменяет папку приложения. На этих этапах временная блокировка Windows (`5`, `32`, `33`) повторяется до 8 попыток с паузой 2 секунды. Ненулевой код завершения самого приложения не повторяется.

Обновите исходники (`git pull --ff-only` в папке репозитория) и повторно запустите `DevlinLauncher.exe` → «Установить». При постоянной блокировке проверьте **Безопасность Windows → Защита от вирусов и угроз → Журнал защиты**, ограничения запуска приложений и права записи в указанную папку. Не отключайте защиту. При управляемой корпоративной политике передайте администратору точный путь и сообщение об отказе.

Полная причина ошибки сохраняется в **`.build/install-error.log`**. Если Windows не позволяет очистить временные файлы, установщик показывает их путь и сохраняет исходную ошибку. Текущая версия остаётся на месте до успешной проверки новой; настройки приложения не затрагиваются. Для диагностики нужны последние строки консоли и этот журнал.

## Сборка и проверка Windows

Ручная сборка без ярлыка и установки WebView2:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\build-windows.ps1
```

Отдельная проверка установленного `.exe` без открытия окна:

```powershell
$report = Join-Path $env:TEMP ('DevlinCheck-' + [guid]::NewGuid().ToString('N') + '.json')
$process = Start-Process .\dist\DevlinDesk\DevlinDesk.exe -ArgumentList @('--self-test', '--self-test-output', ('"' + $report + '"')) -Wait -PassThru
Get-Content $report
```

Проверка пишет новый JSON с `ok: true`; отсутствие отчёта или ненулевой exit code означает ошибку. Пользовательская база в этом режиме не открывается.

GitHub Actions workflow **Windows desktop build** запускается вручную, для тегов `v*` и при изменении кода/установщика в `main`. Он проверяет скрипты в Windows PowerShell 5.1, запускает тесты, собирает `.exe`, проверяет сам бинарник и сохраняет артефакт **DevlinDesk-Windows**. Сборка не подписана сертификатом издателя.

В Linux-среде выполнены тесты приложения, замены/отката сборок, сохранения файлов, обновления Git, безопасной распаковки и режима self-test. Также проверены PowerShell-синтаксис и логика проверки подписей с тестовыми ответами. Настоящая установка Python/WebView2, ярлык и Windows-бинарник проверяются на Windows, а не выдаются за выполненные в Linux.

## Запуск из исходников для разработки

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-desktop.txt
.\.venv\Scripts\python.exe run.py
```

Для браузерного режима добавьте `--browser`, для завершения используйте Ctrl+C. Среда `.venv` разработчика отделена от `.build-venv` установщика.

## Первый проект

Интерфейс использует светлую тему: основной текст — 16 px, подсказки и статусы — не менее 13 px. Уведомления показываются поверх активного окна проекта, профиля или подтверждения и остаются доступными для закрытия. Обычные сообщения видны 10 секунд, ошибки — 20 секунд.

1. Нажмите **Добавить проект**. Название обязательно; сайт и SSH независимы друг от друга.
2. Для сайта укажите HTTP/HTTPS URL, интервал (30 секунд — 1 час), ожидаемые коды и, при необходимости, контрольный текст. Контрольный текст ищется в первом мегабайте ответа. TLS проверяется; неверный сертификат считается ошибкой.
3. Откройте отдельный раздел **SSH-профили** в левой панели → **Добавить SSH-профиль** (или **Создать профиль** в проекте). Укажите хост, порт, пользователя и ключ на ПК, SSH-агент либо пароль. Пароль также используется как фраза зашифрованного ключа. Сохраните профиль.
4. В профиле нажмите **Подтвердить ключ**, сверьте SHA256-отпечаток через доверенную панель хостинга/администратора и подтвердите. Затем нажмите **Тест SSH**. Например, администратор может проверить отпечаток командой `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` для соответствующего алгоритма.
5. В новом или существующем проекте выберите этот **SSH-профиль**. Нажмите **Выбрать папку**, найдите существующую директорию в SSH-проводнике, нажмите **Выбрать эту папку**, затем **Сохранить проект**. Предварительно сохранять проект не нужно. Профиль можно выбрать другой и просмотреть его папки до применения изменений проекта.
6. Нажмите **Проверить сейчас**. Результат появится в карточке и журнале. Фоновые проверки идут, пока приложение работает; проект можно приостановить.

Отпечаток SSH закрепляется для конкретного хоста и порта. Изменившийся ключ блокирует подключение. Если хост/порт изменён в настройках, подтверждение сбрасывается. Приложение никогда не принимает новый ключ автоматически.

Один профиль используется несколькими проектами; каждый проект хранит свой абсолютный путь. Изменение профиля применяется ко всем связанным проектам. Подтверждение ключа в карточке такого проекта также подтверждает ключ общего профиля. Используемый профиль нельзя удалить, пока проекты не переключены на другой. Индивидуальные настройки подключения доступны в раскрываемом блоке **Индивидуальное подключение без профиля**.

Если в приложении нет раздела **SSH-профили** и кнопки **Выбрать папку**, проверьте установленную сборку: полностью завершите приложение через **Выход** в трее, выполните `git pull --ff-only` в корне репозитория и запустите `DevlinLauncher.exe` → «Установить». Установщик собирает текущие локальные исходники; сам запуск Install не скачивает изменения из Git. Откройте именно `dist\DevlinDesk\DevlinDesk.exe`: внизу левой панели должна появиться версия **v1.10.9** и короткий идентификатор коммита. Наведение на номер версии показывает путь запущенного EXE и время сборки. HTML/JS/CSS не кэшируются; проверка установщика также проверяет наличие нового интерфейса профилей и проводника.

Существующие индивидуальные подключения при первом запуске переносятся в профили. Объединяются только подключения с одинаковыми сервером, портом, пользователем, ключом, паролем и подтверждённым отпечатком. До переноса создаётся резервная копия базы в `%LOCALAPPDATA%\DevlinDesk\migration-backups`. `vault.key`, PIN, настройки бота, ключи PHP-проб и пути проектов сохраняются. Для отката на старую версию нужно при полностью закрытом приложении восстановить эту копию как `desk.sqlite3`; перед восстановлением сохраните весь текущий каталог данных отдельно. Ключ шифрования должен оставаться прежним.

Проводник читает каталоги через SFTP с правами SSH-пользователя, без записи и без выполнения команд из имени папки. Доступны домашняя папка, корень, переход вверх, ссылки, навигация по пути и ручной ввод абсолютного пути. Сервер должен поддерживать SFTP. Для очень больших каталогов список ограничен; нужную папку можно открыть по пути. Если SFTP работает в chroot и его пути отличаются от путей shell, после выбора проверьте путь через **Тест SSH**. Git/df требуют Linux/Unix-shell и соответствующие утилиты; одного SFTP-доступа недостаточно.

Тест подключения отделён от проверки папки: успешная аутентификация больше не считается ошибкой SSH при неверном пути. Мониторинг показывает такую ошибку отдельно как **«Папка проекта»**, а Git/SSH-команды возвращают понятную причину без вывода потенциально секретного stderr.

## Telegram

Создайте бота через **@BotFather** и сохраните токен в **Настройки → Telegram-бот**. В поле **Получатель: никнейм или Chat ID** можно указать `@username`, ник без `@` (он нормализуется автоматически), либо числовой Chat ID. После сохранения новых данных приложение проверяет `getMe` и получателя: отображает имя бота, результат проверки, найденный Chat ID и время. **Проверить бота** повторяет проверку без отправки сообщения; **Отправить тест** проверяет доставку и права отправки.

Для **личного аккаунта** сначала отправьте `/start` этому боту, затем сохраните свой ник и проверьте бота. Telegram не позволяет боту первым написать человеку по личному `@username`: приложение ищет соответствующий приватный диалог среди доступных обновлений `getUpdates` и сохраняет найденный Chat ID. Оно не подтверждает обновления (`offset` не передаётся), не меняет их подписку и не отключает webhook. Если обновления уже забирает другой сервис, бот использует webhook или сообщение отсутствует в доступной истории, используйте Chat ID. Аккаунт без username тоже подключается по Chat ID.

Для **публичного канала или супергруппы** используйте их `@username`; для закрытой группы — отрицательный Chat ID. У бота должны быть права отправки (для канала обычно права администратора). Статус «Бот доступен» подтверждает токен и получателя, а не гарантирует доставку: нажмите **Отправить тест**. При смене токена или адресата предыдущая проверка сбрасывается. Данные последней проверки хранятся локально; статус не является непрерывной проверкой Telegram.

Реальный Telegram вызывается после указания настроек и соответствующих действий/проверок. При мониторинге нужны доступ к `api.telegram.org` и разрешения бота. Токен не раскрывается в статусе или сообщениях об ошибке.

Бот уведомляет о:

- недоступном сайте, неожиданном HTTP-коде или отсутствующем контрольном тексте;
- ошибках SSH/Git и диска;
- падении свободного места ниже порога;
- новом наборе изменений файлов;
- автоматических коммитах;
- восстановлении нормальной работы, если эта опция включена.

Одинаковая проблема не отправляется заново на каждой проверке. Ошибки доставки записываются в журнал. Долговечной очереди повторной доставки пока нет: при недоступном Telegram проверьте журнал и отправьте тест после восстановления сети.

## Git-профили, GitHub и GitLab

Git-команды выполняются **на сервере проекта**, а не в Windows-папке приложения. Для авторизации через профиль нужен Git **2.31+** на сервере. GitHub/GitLab API используется для проверки аккаунта и выбора репозитория; изменения отправляются обычным push в ветку, без Merge Request.

**SSH-профиль даёт доступ к серверу, Git-профиль — к GitHub/GitLab.** Один Git-профиль можно выбрать в нескольких проектах. Токен хранится зашифрованно в локальной базе; интерфейс не возвращает его при чтении профиля. Смена сервиса/адреса сбрасывает прежний токен. Используемый профиль нельзя удалить.

1. В левой панели откройте **Git-профили → Добавить Git-профиль**.
2. Выберите GitHub либо GitLab, задайте название и персональный токен. При необходимости заполните **Имя автора** и **Email автора** — оба поля вместе. Для GitLab можно указать HTTPS адрес собственного сервера без пути. GitHub Enterprise пока не поддерживается.
3. Для GitHub fine-grained токену нужны выбранные репозитории, **Contents: Read and write**, **Metadata: Read**; classic токену — `repo`. Для GitLab используйте `api` и `write_repository`. Срок действия, одобрение организации, SSO, роль пользователя и защита ветки также влияют на доступ.
4. Сохраните профиль и нажмите **Проверить авторизацию**. Проверяется аккаунт; права записи в конкретную ветку проверяются фактическим push.
5. В настройках проекта выберите **Git-профиль**, сохраните проект, откройте **Git & файлы**. Приложение покажет наличие локального Git и `origin`. **Проверить репозиторий** проверяет чтение с SSH-сервера (`ls-remote`).
6. Если репозиторий не подключён, нажмите **Подключить репозиторий → Выбрать из моего аккаунта**, выберите репозиторий и подтвердите. Список доступен постранично; также можно ввести HTTPS URL вручную. Репозиторий должен уже существовать в сервисе — его создание производится в GitHub/GitLab.

Подключение сначала проверяет доступ с сервера, затем создаёт локальный Git при необходимости и добавляет `origin`. Оно не делает clone/pull и не меняет файлы или историю. Для существующего локального Git без `origin` добавляется только адрес. Замена существующего `origin` требует явного подтверждения и убирает отдельный `pushurl`. При первоначальной выгрузке файлов выбирайте пустой удалённый репозиторий; существующая удалённая история не перезаписывается.

Git-профили работают с **HTTPS origin того же сервиса**. Если раньше origin был SSH, используйте **Настроить подключение репозитория** для выбора HTTPS адреса и подтвердите замену. Токен передаётся через stdin SSH-команды и временное окружение процесса Git; в URL, командную строку, файлы и Git-конфигурацию он не записывается. Перенаправления отключены, TLS проверяется. Токен во время операции доступен серверу и процессам с соответствующими правами: выбирайте доверенный SSH-сервер.

Без Git-профиля сохраняется прежний способ: SSH-ключ с правом записи и проверенным ключом Git-хостинга в `known_hosts`, либо HTTPS с credential helper сервера. Пароли и токены в URL запрещены. SSH Git использует `BatchMode=yes`, `StrictHostKeyChecking=yes`; для нестандартного ключа настройте `IdentityFile` на сервере.

Автор выбирается в следующем порядке: **Git-профиль → настройки Git на сервере → общие настройки приложения**. Пустые поля профиля сохраняют автора существующего проекта. Имя, email и источник показываются над списком коммитов. Значения применяются только к текущему `git commit`; локальная и глобальная конфигурация сервера не перезаписываются.

### Ошибка коммита и диагностика хостинга

В **Git & файлы → Диагностика Git** доступны проверки установки Git, автора, прав записи `.git/objects/refs`, `index.lock` и обязательной подписи коммитов. Это чтение настроек: файлы, блокировки, права и настройки подписи автоматически не меняются.

Ошибка показывает этап: проверка содержимого (с именем файла), добавление файлов в индекс или создание коммита. Предварительная проверка читает исходные байты без clean-фильтров; символические ссылки учитываются по строке цели, без чтения файла или каталога по ссылке. Диагностика также проверяет хеширование изменённых файлов. При добавлении и коммите правила Git-фильтров и hooks сохраняются.

Для ошибок Git (включая код 128) приложение распознаёт исчерпанную квоту, `safe.directory`, блокировку индекса, недоступные права, неверного автора и проблемы подписи. Произвольный stderr скрывается, поскольку может содержать токены. Проверьте квоту в панели хостинга даже при зелёной диагностике прав. При ошибке commit-hook или записи объекта staged-изменения сохраняются: после исправления причины завершите коммит на сервере либо согласуйте индекс вручную. Не удаляйте `index.lock`, пока другая Git-операция ещё работает; для `safe.directory` используйте только доверенный абсолютный путь проекта, а не `*`.

### Изменения уже сделаны на сервере

Откройте проект → **Git & файлы** → **Обновить**. Посмотрите изменения, выберите файлы, откройте diff, задайте сообщение и нажмите **Создать коммит**. Подтверждение показывает список файлов. Ручной коммит создаётся **только на сервере**, без push. Затем в разделе **Коммиты на отправку** можно проверить хеши, сообщения, авторов и даты и отдельно нажать **Отправить коммиты**.

Если файлы изменились после просмотра, приложение запросит обновление списка. Уже staged-изменения не включаются в чужой коммит: нужно сначала разобраться с ними на сервере. В случае ошибки commit-hook приложение не делает reset, не удаляет файлы и не откатывает индекс; исправьте hook и завершите операцию вручную.

**Обновить с origin** получает удалённую историю без изменения рабочих файлов. Перед отправкой список обновляется повторно; подтверждение показывает все коммиты текущей ветки, которые будут отправлены. При большом количестве отображаются последние 50, а счётчик показывает полный объём. Если HEAD, ветка или origin изменились после подтверждения, отправка останавливается и нужен новый просмотр. Если на origin есть коммиты, отсутствующие на сервере, push блокируется до согласования истории.

При ошибке push локальные коммиты сохраняются. Исправьте доступ и повторите **Отправить коммиты**, без создания дубликата.

**Загрузить из Git** выполняет `pull --ff-only origin <текущая ветка>` только при чистой директории. При расхождении истории требуется ручное решение на сервере. Force push, reset, rebase и автоматическое слияние не выполняются.

Можно задать **ветку для синхронизации** в настройках проекта. Если реальная ветка сервера отличается, запись/push/pull останавливаются. Приложение не переключает ветки автоматически. Если поле пусто, используется текущая ветка сервера.

### На сервере ещё нет репозитория

Создайте **пустой** репозиторий в GitHub/GitLab без README/начального коммита. Подключите его через **Подключить репозиторий**, затем выберите файлы и подтвердите **Создать коммит**. Проверьте список **Коммиты на отправку** и выполните отдельную отправку. Без предварительного подключения также доступна кнопка **Подключить и создать коммит**: URL, начальная ветка и выбранные файлы. Существующая директория и её файлы сохраняются.

Предварительный список учитывает существующий `.gitignore` ещё до создания локального Git, поэтому исключённые файлы не попадают в первый коммит. Если `.git` уже существует, приложение использует текущий репозиторий и сохраняет историю и настройки. При повреждённых метаданных или недоступном Git операция останавливается с объяснением; существующая `.git` не переинициализируется.

Если проект лежит внутри другого Git-репозитория, операция останавливается: нужно указать его настоящий корень. Если удалённый репозиторий уже содержит другую историю, список покажет отсутствующие на сервере коммиты и отправка остановится; приложение не перезаписывает её.

### Создание и редактирование .gitignore

В проекте откройте **Git & файлы**. Блок **.gitignore** проверяет файл в корне серверной папки и предлагает **Создать .gitignore** либо **Редактировать .gitignore**. Функция работает и до подключения Git-репозитория.

В редакторе можно изменять текст существующих правил и комментариев. Кнопка **Выбрать файлы и папки** открывает SFTP-проводник внутри проекта: отметьте файл или всю папку, либо нажмите **Открыть**, чтобы выбрать отдельные элементы внутри неё. Выбор сохраняется при переходе между папками; поиск фильтрует текущую папку. **Добавить правила** добавляет выбранные пути к тексту, затем **Сохранить .gitignore** записывает изменения после подтверждения. Повторяющиеся точные правила не добавляются. Папка получает правило `/путь/`, файл — `/путь`; специальные символы в реальных именах экранируются. Шаблоны вроде `*.log` можно вписать вручную.

Существующие файлы проекта не удаляются. **Уже отслеживаемые Git файлы не перестают отслеживаться** от добавления в `.gitignore`; редактор не выполняет `git rm --cached`. Сохранение обновляет список изменений. Затем `.gitignore` можно включить в отдельный коммит и отправить обычным push. При включённой автоматической синхронизации изменение обрабатывает мониторинг.

Редактор поддерживает UTF-8 до 256 КБ и сохраняет права существующего файла. Если файл изменился после открытия, запись блокируется: скопируйте свои правила, откройте редактор заново и согласуйте изменения. Проводник показывает до 1000 элементов каталога, не выходит за пределы проекта и не открывает `.git` или папки-ссылки. Сам файл `.gitignore`, если он является ссылкой, не редактируется.

### Автоматическая синхронизация

Включается отдельно в настройках проекта, с подтверждением. При каждой проверке допустимые изменения становятся новым коммитом; опция **Отправлять автоматические коммиты** включает push в текущую/закреплённую ветку. По умолчанию автоматические коммиты выключены. Если ветка GitLab защищена, дайте ключу право push или используйте отдельную рабочую ветку.

Существующий `.gitignore` учитывается Git. Дополнительно исключаются `.env` (кроме примеров), приватные ключи, `credentials.json`, `auth.json`, базы/SQL/backup-файлы и каталоги `.git`, `.ssh`, `.venv`, `node_modules`, `vendor`, `__pycache__`, `.idea`. Появление потенциально секретного или staged-файла останавливает автосинхронизацию. **Фильтр имени не выявляет все секреты внутри обычных исходников:** проверяйте содержимое перед выгрузкой, используйте `.gitignore` и правила своего GitLab.

Одна операция ограничена 2000 изменениями/файлами. Текстовый просмотр нового файла ограничен 100 КБ, diff — 200 КБ. Зависимости, медиаархивы и большие базы следует исключать из Git-проекта. Символьные ссылки не разыменовываются для просмотра новых файлов.

## Свободное место

По умолчанию приложение вызывает `df -Pk` по SSH и получает свободное место **файловой системы, где расположен проект**. Это не размер директории и не индивидуальная квота хостинга. Порог задаётся в процентах оставшегося места.

### Хостинг с лимитом тарифа

`df` и PHP `disk_free_space` обычно возвращают общий диск сервера, поэтому терабайты на экране не означают доступную квоту вашего аккаунта. Для хостинга откройте **SSH-профили → Настроить → Это хостинг — считать остаток по тарифу**. Укажите объём из тарифа, единицу **GB/ГБ** либо **GiB/ГиБ** и **корневую папку всего аккаунта**. Папку можно выбрать проводником после сохранения SSH-профиля и подтверждения ключа. Затем сохраните профиль и нажмите **Тест SSH** либо **Проверить сейчас** в проекте.

Например, если все сайты лежат в `/var/www/h149071/data/www/`, выберите `/var/www/h149071/data`, когда именно эта папка содержит все данные аккаунта. Не выбирайте только `devlin.by`: остальные сайты также занимают общий тариф. Проверьте структуру папок в панели хостинга — пример не гарантирует полноту учёта на конкретном сервере.

Приложение выполняет `du -sk` по всей выбранной папке, включая скрытые файлы и `.git`, и показывает **оценку остатка = лимит тарифа − занятый объём**, с размером аккаунта, путём и предупреждением о превышении. Все проекты SSH-профиля используют один лимит; размер проекта не вычитается повторно. Проект вне папки аккаунта требует исправления пути профиля. При недоступных каталогах или тайм-ауте частичное измерение не считается свободным местом. На большом аккаунте измерение может занять до 90 секунд; учитывайте это при выборе интервала.

Режим хостинга имеет приоритет над SSH/HTTP настройкой диска проекта: сохранённая PHP-проба больше не используется для места. **Выключено** отключает измерение. Уведомления о низком остатке используют прежний процентный порог, но помечаются как оценка тарифа.

Это **оценка по папке**, а не системная квота: почта, базы данных, резервные копии и другие данные вне неё, ограничения по числу файлов и особенности учёта провайдера могут отличаться. Точная квота и остаток доступны в панели хостинга. Автоматическое получение точной квоты требует API конкретного провайдера; универсального ответа у PHP-пробы нет.

Альтернатива — защищённая **PHP-проба**:

1. Убедитесь, что сервер выполняет PHP 8+, проект находится в web-root и доступен по HTTPS.
2. Подтвердите SSH, выберите папку проекта и нажмите **Установить PHP-пробу**. В окне укажите фактический HTTPS URL файла и нажмите **Установить и настроить**. В выбранную папку будет добавлен `.devlin-disk.php`; существующий файл не перезаписывается.
3. Ключ сохраняется в приложении и показывается один раз. PHP-файл содержит только SHA256-хеш ключа, возвращает JSON `{"free": ..., "total": ...}` и не выполняет команды из запроса.
4. URL, ключ и режим HTTP сохраняются вместе автоматически. Адрес на основе сайта предлагается только как редактируемая подсказка: проверьте его соответствие выбранной папке. Для существующей пробы можно вручную указать её URL и ключ в настройках проекта. Пустое поле ключа сохраняет действующее значение.
5. Сервер должен передавать `Authorization: Bearer <ключ>` в PHP. Для Nginx обычно нужен `fastcgi_param HTTP_AUTHORIZATION $http_authorization;`; на Apache проверьте передачу заголовка в вашу конфигурацию PHP/FastCGI. Не помещайте ключ в URL.
6. Нажмите **Проверить сейчас**. Перенаправления для пробы запрещены, чтобы не отправить ключ другому адресу.

Если PHP-файл расположился вне document-root или сервер не выполняет PHP, используйте SSH-проверку; настройку web-сервера приложение не меняет. Удалённый PHP-файл автоматически не удаляется при удалении карточки проекта.

## Данные и PIN

На Windows данные хранятся в `%LOCALAPPDATA%\DevlinDesk`: SQLite-база, `vault.key`, лог приложения. Доступен параметр `--data-dir <папка>` или переменная `DEVLIN_DATA_DIR`. На Linux путь по умолчанию — `$XDG_DATA_HOME/devlin-desk` или `~/.local/share/devlin-desk`; на macOS — `~/Library/Application Support/DevlinDesk`.

Пароли SSH, токены Telegram и PHP-пробы зашифрованы Fernet. Ключ шифрования находится **на этом же компьютере**: шифрование защищает от простого чтения базы, но не от пользователя с доступом к базе и ключу. Используйте права Windows и BitLocker. Не публикуйте каталог данных. Для резервной копии закройте приложение и скопируйте **весь каталог**, включая `vault.key`. Без ключа сохранённые секреты не восстановить.

PIN хранится как scrypt-хеш. Он закрывает доступ к интерфейсу, но не шифрует весь диск. После пяти неверных попыток — задержка на минуту. Кнопка блокировки доступна после установки PIN; мониторинг продолжается при блокировке. Забытого PIN приложение не отправляет и не показывает: восстановление требует работы с вашей локальной копией данных; не удаляйте её без резервной копии.

На один каталог данных разрешён один экземпляр приложения, чтобы не дублировать проверки и автоматические коммиты. В браузерном режиме не открывайте локальный API для сети: предусмотрен только loopback, защита Origin/Host и сессионная HttpOnly-cookie.

### Серверный SSH-ключ для GitHub/GitLab

Ключ подключения приложения к серверу и ключ подключения сервера к Git-хостингу — разные ключи. Для серверной авторизации выберите SSH URL (`git@github.com:owner/repository.git`) и не назначайте Git-профиль с HTTPS-токеном. В каталоге проекта можно указать нестандартный серверный ключ:

```bash
git config --local core.sshCommand "ssh -i '$HOME/.ssh/devlin_git_ed25519' -o IdentitiesOnly=yes"
git ls-remote origin
```

Приложение сохраняет выбор ключа из серверного `GIT_SSH_COMMAND` или `core.sshCommand`; без них используется обычный `ssh` с `~/.ssh/config`. Git-команды выполняются без интерактивного ввода и с проверкой известного ключа хостинга. До проверки в приложении подтвердите отпечаток хостинга через серверную консоль после сверки с официальной документацией. Успешный `ssh -T git@github.com` проверяет авторизацию аккаунта; `git ls-remote origin` проверяет чтение конкретного репозитория, а права записи и защищённая ветка проверяются при push.


В окне «Подключить репозиторий» без Git-профиля доступно поле **SSH-ключ на сервере**: например `~/.ssh/devlin_git_ed25519`. Приложение проверяет наличие файла и доступ к репозиторию выбранным ключом, затем сохраняет `core.sshCommand` только для этого проекта. Содержимое приватного ключа не читается и не передаётся на ПК. Подтвердите ключ Git-хостинга через консоль заранее; ключ с паролем требует доступного в SSH-сеансе агента. Если серверная переменная `GIT_SSH_COMMAND` перекрывает настройки Git, приложение объяснит это и не сохранит неработающую настройку. Кнопка **Использовать SSH вместо HTTPS** предлагает адрес для GitHub.com/GitLab.com; изменение origin требует подтверждения.

Для обновления **Devlin Desk** запускайте **DevlinLauncher.exe → «Обновить» на ПК**, в репозитории `jobs_dashboard` либо в `dist`. Команда `git pull` в каталоге сайта на хостинге относится к сайту, а не к приложению. Номер запущенной версии отображается в левой панели и в окне подключения репозитория.


### Обновление остановилось с WinError 32/33

Новая сборка может пройти все проверки, но не установиться, если процесс удерживает старую папку. Лаунчер v1.10.3 задаёт временную рабочую папку своей дочерней копии: запуск из `dist` больше не должен блокировать перенос старой версии из-за унаследованного CurrentDirectory. Windows-проверка лаунчера запускает дочерний процесс и переименовывает условную папку установки, пока дочерний процесс работает.

При переходе со старого лаунчера завершите его, выйдите из приложения через трей и закройте терминалы/редакторы, открытые внутри `dist\DevlinDesk`. Обновите **репозиторий jobs_dashboard на ПК** через `git pull --ff-only` из корня исходников и запустите новый корневой `DevlinLauncher.exe`. Заголовок журнала должен показывать **Launcher 1.10.3**. Неудачная установка сохраняет старую версию и данные; процессы установщик не завершает. Если ошибка 32 сохраняется, найдите удерживающий папку процесс через поиск дескрипторов в Мониторе ресурсов Windows и завершите его обычным способом.


### Кнопка создания коммита недоступна

Если на сервере уже есть подготовленные (staged) изменения, приложение не включает их автоматически в новый коммит. В предупреждении над списком нажмите **Убрать подготовку к коммиту**, проверьте список и подтвердите. Операция меняет только индекс: файлы остаются в текущем состоянии, история и существующие коммиты сохраняются. Работает также до первого коммита, когда HEAD ещё отсутствует. После обновления списка выберите файлы, создайте коммит и отправьте его отдельно. Если индекс или файлы изменились после просмотра либо есть конфликты слияния, действие остановится.


### Ход операций и ограничения Git на хостинге

При нажатии кнопок появляется постоянная плашка со спиннером, названием операции и прошедшим временем. Она видна поверх открытого диалога до завершения, ошибки или отмены подтверждения; ошибки выводятся отдельным уведомлением. В режиме хостинга SSH-профиля добавление файлов выполняется с `core.preloadIndex=false`, `index.threads=1`, `pack.threads=1` только для данной команды. Постоянные настройки Git не меняются. Сообщения различают квоту диска, лимиты процессов/памяти/открытых файлов, повреждённый индекс и отказ записи объектов. По одному коду 128 точная причина неизвестна; приложение не удаляет индекс и не отключает Git-фильтры.

В v1.10.6 Git добавляет каждый выбранный путь отдельно, независимо от размера списка. Ошибка на одном файле указывает именно этот путь; уже подготовленные файлы сохраняются. В интерфейсе отображается фактический счётчик подготовки и этап создания/отправки коммитов, полученные через защищённый API состояния операции. Индикатор использует отдельный верхний слой браузера (manual popover), поэтому остаётся видимым при прокрутке проекта и при открытии подтверждений. После частичного отказа нажмите «Убрать подготовку к коммиту» перед новым выбором файлов.

В v1.10.7 имена файлов в выводе Git читаются без потери исходных байтов. Файлы с именами не в UTF-8 (например MP3 с кириллицей в CP1251) можно выбрать, просмотреть и включить в коммит без переименования на сервере. Для таких имён интерфейс показывает подсказку CP1251 и отметку «имя в байтах»; команды Git и проверки содержимого используют точное исходное имя, а не подсказку. Имена с буквальной обратной косой чертой также сохраняются и не смешиваются с байтовыми идентификаторами.

В v1.10.8 при недоступной существующей `.git` приложение автоматически выполняет диагностику и показывает доступные исправления во вкладке «Git & файлы», а также в «Диагностика Git». Для блокировки `safe.directory` кнопка «Доверять папке проекта» добавляет только её абсолютный путь в настройки текущего SSH-пользователя после подтверждения. При недостающих правах владельца можно восстановить чтение файлов и доступ к папкам `.git`, если всё дерево принадлежит текущему пользователю и не содержит ссылок. Права остальных пользователей и защита Git-объектов от записи сохраняются. Для другого владельца или недоступного дерева выберите SSH-профиль владельца проекта через настройки приложения: текущий SSH-пользователь не получает дополнительных системных привилегий. Повреждённая `.git` не удаляется и не создаётся заново.

При конфликте Git-профиля с SSH-адресом origin кнопка «Подключить через Git-профиль» предлагает HTTPS-адрес того же репозитория на том же сервисе. Токен проверяется через API сервиса и с SSH-сервера; адреса fetch/push заменяются только после успешной проверки и повторной проверки состояния. Файлы сайта, индекс и коммиты сохраняются. Все действия требуют подтверждения внутри приложения; команды в консоли хостинга для этих исправлений не нужны.

В v1.10.9 для нераспознанной `.git` диагностика проверяет отдельно `HEAD`, `objects`, `refs` и `config`, а также файл ссылки `.git` после переноса проекта с другого ПК. Общая ошибка больше не повторяется в нескольких блоках. Кнопка «Восстановить HEAD» доступна для отсутствующего/некорректного HEAD, когда выбранную ветку можно определить без догадок; перед изменением сохраняется копия всех метаданных, индекс и объекты остаются на месте.

Кнопка «Сохранить .git и настроить заново» — отдельный вариант для неисправной структуры, требующий подтверждения **начала новой пустой истории**. Исходная `.git` целиком переносится в приватную папку `~/.devlin-git-backups/<идентификатор проекта>/<идентификатор копии>/original.git`, путь копии выводится в уведомлении и журнале. Это не переносит старые коммиты в активный Git: исходная .git сохраняется в копии. Если .git была файлом ссылки, сохраняется сама ссылка; внешний Git-каталог не копируется и не изменяется. Файлы сайта не меняются; после операции origin подключается через интерфейс. Новый Git подготавливается до перемещения старой `.git`; при отказе переноса/установки приложение пытается вернуть исходную `.git`, не перезаписывая появившиеся метаданные. Недоступное или чужое дерево и ссылки внутри него не переустанавливаются автоматически.
