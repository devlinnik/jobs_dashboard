# Devlin Desk

Локальное приложение для Windows: проекты, мониторинг сайтов, SSH, свободное место на серверах, Git и уведомления Telegram. Интерфейс на русском языке, работает в отдельном окне. Python + FastAPI + pywebview; данные — SQLite, интерфейс — HTML/CSS/JS без внешних CDN.

## Установка на Windows — двойным щелчком

Скачайте или клонируйте репозиторий в папку, доступную для записи, и запустите **`Install-Devlin.cmd`** в корне. Нужны Windows 10/11 x64, интернет для первой установки/обновления и несколько гигабайт свободного места для среды сборки. Git не обязателен при установке из ZIP.

Установщик:

1. Проверит Python 3.12 x64; при отсутствии скачает официальный установщик Python 3.12.10 с `python.org` и установит для текущего пользователя.
2. Проверит Microsoft Edge WebView2 Runtime; при отсутствии установит официальный Evergreen Runtime Microsoft. Windows может запросить подтверждение или перезагрузку.
3. **До запуска скачанных установщиков проверит Authenticode-подпись и точное имя издателя**: Python Software Foundation либо Microsoft Corporation. Ошибка подписи останавливает установку; проверка TLS не отключается.
4. Создаст отдельную среду `.build-venv` и соберёт приложение через PyInstaller во временной папке `.build`.
5. Запустит новую сборку в режиме `--self-test`: проверка локального API, HTML, JS и CSS, без окна и без пользовательских данных.
6. Разместит проверенную сборку в **`dist\DevlinDesk`** и создаст ярлык **Devlin Desk** на рабочем столе текущего пользователя.

В результате:

```text
jobs_dashboard/
  Install-Devlin.cmd         установка / повторная сборка локальных исходников
  Update-Devlin.cmd          обновление и пересборка
  Start-Devlin.cmd           запуск установленного приложения
  dist/                     не попадает в Git
    DevlinDesk/
      DevlinDesk.exe
      Start-Devlin.cmd
      Update-Devlin.cmd      обновление прямо из папки приложения
      install-info.json
      _internal/            обязательные библиотеки и интерфейс
      _maintenance/         автономные файлы обновления
```

**`Start-Devlin.cmd` в корне** открывает установленный `.exe`; если сборки ещё нет, автоматически выполняет первую установку и затем запускает её. Сам установщик после завершения не открывает окно: можно нажать ярлык или `.exe`.

Батники запускают PowerShell с `ExecutionPolicy Bypass` **только для этого процесса**. Политика пользователя/компьютера не меняется. Корпоративная Group Policy может запрещать выполнение даже в этом режиме; в таком случае разрешение должен дать администратор, скрипт его не обходит. Если ярлык не удалось создать, установка остаётся успешной и показывает путь к `.exe`.

Приложение слушает только 127.0.0.1 и выбирает свободный порт. Закрытие окна завершает мониторинг после завершения активных SSH/Git-операций. Сворачивание окна не останавливает проверки. Автозапуск Windows и фоновая служба пока не добавлены.

## Обновление приложения

Закройте Devlin Desk и запустите **`Update-Devlin.cmd`** в корне либо рядом с `.exe` в `dist\DevlinDesk`.

- В чистом Git-checkout на ветке `main` обновление получает `origin/main` и применяет **только fast-forward**. Разошедшаяся история останавливает обновление; reset/force не выполняются.
- Если есть локальные изменения, Git не установлен либо выбрана другая ветка, ваши исходники сохраняются и **собирается текущая локальная версия**. Сообщение об этом видно в окне установщика.
- Для ZIP-версии или переносимой сборки без исходников обновление скачивает текущий `main` из `devlinnik/jobs_dashboard` через HTTPS в отдельную временную папку. Оригинальная папка исходников не перезаписывается. Адрес репозитория закреплён в коде.
- Если вы дорабатываете ZIP-исходники локально и хотите собрать их вместо версии GitHub, используйте **`Install-Devlin.cmd`** либо `Update-Devlin.cmd -Local` из корня. Локальный режим требует сохранённой папки исходников.

Новая версия сначала собирается и проверяется отдельно. До этого текущая сборка не меняется. Запущенное приложение **не завершается принудительно**: обновление попросит его закрыть. Параллельные установки блокируются.

Перед заменой текущая версия переносится в **`dist\DevlinDesk.previous-ДАТА-ИД`**. Эти копии не удаляются автоматически и не перезаписывают предыдущие резервные версии. Если финальная замена не удалась, старая папка возвращается. Время в имени резервной копии — местное время вашего ПК.

Для ручного отката закройте приложение, сохраните неудачную папку отдельно и верните нужной `DevlinDesk.previous-*` имя `DevlinDesk`, чтобы ярлык снова указывал на неё. Резервные сборки можно удалить вручную после проверки новой версии.

**Проекты, PIN, SSH-доступы и токены сохраняются**: установщик не читает и не удаляет `%LOCALAPPDATA%\DevlinDesk`. Он не выполняет миграций рабочей базы при проверке сборки; проверка использует временные данные. Если в будущих версиях изменится схема базы, разработчик должен добавить совместимую миграцию в приложение. Старый бинарник может быть несовместим с новой схемой: перед большим обновлением делайте резервную копию каталога данных.

Обновление из `dist` копирует служебные файлы в TEMP и работает оттуда: Windows не удерживает файлы внутри заменяемой папки. Переносите **всю папку `DevlinDesk`**, включая `_internal` и `_maintenance`. Если исходный checkout больше недоступен, updater использует отдельный кеш `%LOCALAPPDATA%\DevlinDeskUpdater` и получает исходники из GitHub. Для запуска готового `.exe` Python не нужен; для самостоятельной пересборки updater установит его при необходимости.

Папки `dist`, `.build`, `.build-venv`, старые сборки и временные файлы обновления исключены из Git. В репозитории хранятся только исходники и воспроизводимые команды сборки.

### Если установка завершилась с `WinError 5` (отказано в доступе)

Успешная сборка EXE ещё не означает завершённую установку: затем установщик копирует файлы, запускает проверку EXE и заменяет папку приложения. На этих этапах временная блокировка Windows (`5`, `32`, `33`) повторяется до 8 попыток с паузой 2 секунды. Ненулевой код завершения самого приложения не повторяется.

Обновите исходники (`git pull --ff-only` в папке репозитория) и повторно запустите `Install-Devlin.cmd`. При постоянной блокировке проверьте **Безопасность Windows → Защита от вирусов и угроз → Журнал защиты**, ограничения запуска приложений и права записи в указанную папку. Не отключайте защиту. При управляемой корпоративной политике передайте администратору точный путь и сообщение об отказе.

Полная причина ошибки сохраняется в **`.build/install-error.log`**. Если Windows не позволяет очистить временные файлы, установщик показывает их путь и сохраняет исходную ошибку. Текущая версия остаётся на месте до успешной проверки новой; настройки приложения не затрагиваются. Для диагностики нужны последние строки консоли и этот журнал.

## Сборка и проверка Windows

Ручная сборка без ярлыка и установки WebView2:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\build-windows.ps1
```

Отдельная проверка установленного `.exe` без открытия окна:

```powershell
$report = Join-Path $env:TEMP ('DevlinCheck-' + [guid]::NewGuid().ToString('N') + '.json')
$process = Start-Process .\dist\DevlinDesk\DevlinDesk.exe -ArgumentList @('--self-test', '--self-test-output', ('"' + $report + '"')) -Wait -PassThru
Get-Content $report
```

Проверка пишет новый JSON с `ok: true`; отсутствие отчёта или ненулевой exit code означает ошибку. Пользовательская база в этом режиме не открывается.

GitHub Actions workflow **Windows desktop build** запускается вручную, для тегов `v*` и при изменении кода/установщика в `main`. Он проверяет скрипты в Windows PowerShell 5.1, запускает тесты, собирает `.exe`, проверяет сам бинарник и сохраняет артефакт **DevlinDesk-Windows**. Сборка не подписана сертификатом издателя.

В Linux-среде выполнены тесты приложения, замены/отката сборок, сохранения файлов, обновления Git, безопасной распаковки и режима self-test. Также проверены PowerShell-синтаксис и логика проверки подписей с тестовыми ответами. Настоящая установка Python/WebView2, ярлык и Windows-бинарник проверяются на Windows, а не выдаются за выполненные в Linux.

## Запуск из исходников для разработки

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-desktop.txt
.\.venv\Scripts\python.exe run.py
```

Для браузерного режима добавьте `--browser`, для завершения используйте Ctrl+C. Среда `.venv` разработчика отделена от `.build-venv` установщика.

## Первый проект

1. Нажмите **Добавить проект**. Название обязательно; сайт и SSH независимы друг от друга.
2. Для сайта укажите HTTP/HTTPS URL, интервал (30 секунд — 1 час), ожидаемые коды и, при необходимости, контрольный текст. Контрольный текст ищется в первом мегабайте ответа. TLS проверяется; неверный сертификат считается ошибкой.
3. Для SSH укажите хост, порт, пользователя и **абсолютный путь** к существующей директории проекта. Поддерживаются серверы Linux/Unix с `sh`, `df`, `find` и Git. Приложение не создаёт эту директорию.
4. Выберите файл приватного SSH-ключа на вашем ПК, SSH-агент либо пароль. Поле пароля также используется как фраза зашифрованного ключа. У пользователя сервера должны быть права на проект.
5. Сохраните проект. В его карточке нажмите **Подтвердить ключ**, сверьте SHA256-отпечаток через доверенную панель хостинга/администратора и подтвердите. Затем нажмите **Тест SSH**. Например, администратор может проверить отпечаток командой `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`.
6. Нажмите **Проверить сейчас**. Результат появится в карточке и журнале. Фоновые проверки идут, пока приложение работает; проект можно приостановить.

Отпечаток SSH закрепляется для конкретного хоста и порта. Изменившийся ключ блокирует подключение. Если хост/порт изменён в настройках, подтверждение сбрасывается. Приложение никогда не принимает новый ключ автоматически.

## Telegram

Создайте бота через **@BotFather**, начните с ним диалог командой `/start`, получите Chat ID и сохраните их в **Настройки → Telegram-бот**. Для групп Chat ID обычно отрицательный; у бота должно быть право отправлять сообщения в нужный чат. Если нужного Chat ID ещё нет, его можно получить через Telegram Bot API или доверенный инструмент, не раскрывая токен посторонним сервисам.

После сохранения нажмите **Отправить тест**. Реальный Telegram не вызывается до указания ваших настроек и соответствующих действий/проверок. При мониторинге нужны доступ к `api.telegram.org` и разрешения бота.

Бот уведомляет о:

- недоступном сайте, неожиданном HTTP-коде или отсутствующем контрольном тексте;
- ошибках SSH/Git и диска;
- падении свободного места ниже порога;
- новом наборе изменений файлов;
- автоматических коммитах;
- восстановлении нормальной работы, если эта опция включена.

Одинаковая проблема не отправляется заново на каждой проверке. Ошибки доставки записываются в журнал. Долговечной очереди повторной доставки пока нет: при недоступном Telegram проверьте журнал и отправьте тест после восстановления сети.

## Git и GitLab

Git-команды выполняются **на сервере проекта**, а не в Windows-папке приложения. Git должен быть установлен на сервере. GitLab работает через обычный `origin`, без Merge Request и без GitLab API.

**Авторизация приложения по SSH на сервер и авторизация сервера в GitLab — разные подключения.** На сервере настройте отдельный SSH-ключ с правом записи в репозиторий и подтвердите ключ Git-хостинга в `known_hosts` через доверенный канал. Поддерживается HTTPS с уже настроенным credential helper сервера. Пароли и токены в URL репозитория запрещены. Git-запросы неинтерактивны; SSH Git требует проверенный ключ хоста и использует `BatchMode=yes`, `StrictHostKeyChecking=yes`. При нестандартном ключе настройте `IdentityFile` в SSH-конфигурации сервера.

В **Настройках** задайте имя и email автора коммитов. Эти значения применяются к команде `git commit` и не перезаписывают глобальный Git-конфиг сервера.

### Изменения уже сделаны на сервере

Откройте проект → **Git & файлы** → **Обновить**. Посмотрите изменения, выберите файлы, откройте diff, задайте сообщение и нажмите **Создать коммит**. Подтверждение показывает список файлов. Можно сразу отправить коммит в origin либо создать его только на сервере.

Если файлы изменились после просмотра, приложение запросит обновление списка. Уже staged-изменения не включаются в чужой коммит: нужно сначала разобраться с ними на сервере. В случае ошибки commit-hook приложение не делает reset, не удаляет файлы и не откатывает индекс; исправьте hook и завершите операцию вручную.

Если коммит создан, но push не прошёл, это явно показывается. Коммит остаётся на сервере. После исправления доступа нажмите **Отправить коммиты**, а не создавайте дубликат.

**Загрузить из Git** выполняет `pull --ff-only origin <текущая ветка>` только при чистой директории. При расхождении истории требуется ручное решение на сервере. Force push, reset, rebase и автоматическое слияние не выполняются.

Можно задать **ветку для синхронизации** в настройках проекта. Если реальная ветка сервера отличается, запись/push/pull останавливаются. Приложение не переключает ветки автоматически. Если поле пусто, используется текущая ветка сервера.

### На сервере ещё нет репозитория

Создайте **пустой** репозиторий в GitLab без README/начального коммита. В панели Git приложение перечислит уже существующие файлы сервера. Укажите SSH или HTTPS URL, начальную ветку, выберите файлы и подтвердите **Подключить и выгрузить**. Будут выполнены `git init`, `remote add origin`, первый коммит и, если отмечено, push. Существующая директория и её файлы сохраняются.

Если проект лежит внутри другого Git-репозитория, операция останавливается: нужно указать его настоящий корень. Если удалённый репозиторий уже содержит историю, первый push может быть отклонён; приложение не перезаписывает её.

### Автоматическая синхронизация

Включается отдельно в настройках проекта, с подтверждением. При каждой проверке допустимые изменения становятся новым коммитом; опция **Отправлять автоматические коммиты** включает push в текущую/закреплённую ветку. По умолчанию автоматические коммиты выключены. Если ветка GitLab защищена, дайте ключу право push или используйте отдельную рабочую ветку.

Существующий `.gitignore` учитывается Git. Дополнительно исключаются `.env` (кроме примеров), приватные ключи, `credentials.json`, `auth.json`, базы/SQL/backup-файлы и каталоги `.git`, `.ssh`, `.venv`, `node_modules`, `vendor`, `__pycache__`, `.idea`. Появление потенциально секретного или staged-файла останавливает автосинхронизацию. **Фильтр имени не выявляет все секреты внутри обычных исходников:** проверяйте содержимое перед выгрузкой, используйте `.gitignore` и правила своего GitLab.

Одна операция ограничена 2000 изменениями/файлами. Текстовый просмотр нового файла ограничен 100 КБ, diff — 200 КБ. Зависимости, медиаархивы и большие базы следует исключать из Git-проекта. Символьные ссылки не разыменовываются для просмотра новых файлов.

## Свободное место

По умолчанию приложение вызывает `df -Pk` по SSH и получает свободное место **файловой системы, где расположен проект**. Это не размер директории и не индивидуальная квота хостинга. Порог задаётся в процентах оставшегося места.

Альтернатива — защищённая **PHP-проба**:

1. Убедитесь, что сервер выполняет PHP 8+, проект находится в web-root и доступен по HTTPS.
2. Подтвердите SSH и нажмите **Установить PHP-пробу**. В корень будет добавлен `.devlin-disk.php`; существующий файл не перезаписывается.
3. Ключ сохраняется в приложении и показывается один раз. PHP-файл содержит только SHA256-хеш ключа, возвращает JSON `{"free": ..., "total": ...}` и не выполняет команды из запроса.
4. В настройках выберите проверку через PHP-пробу и укажите **фактический HTTPS URL** файла. Автоматически выводить URL из пути SSH ненадёжно, поэтому приложение его не угадывает.
5. Сервер должен передавать `Authorization: Bearer <ключ>` в PHP. Для Nginx обычно нужен `fastcgi_param HTTP_AUTHORIZATION $http_authorization;`; на Apache проверьте передачу заголовка в вашу конфигурацию PHP/FastCGI. Не помещайте ключ в URL.
6. Нажмите **Проверить сейчас**. Перенаправления для пробы запрещены, чтобы не отправить ключ другому адресу.

Если PHP-файл расположился вне document-root или сервер не выполняет PHP, используйте SSH-проверку; настройку web-сервера приложение не меняет. Удалённый PHP-файл автоматически не удаляется при удалении карточки проекта.

## Данные и PIN

На Windows данные хранятся в `%LOCALAPPDATA%\DevlinDesk`: SQLite-база, `vault.key`, лог приложения. Доступен параметр `--data-dir <папка>` или переменная `DEVLIN_DATA_DIR`. На Linux путь по умолчанию — `$XDG_DATA_HOME/devlin-desk` или `~/.local/share/devlin-desk`; на macOS — `~/Library/Application Support/DevlinDesk`.

Пароли SSH, токены Telegram и PHP-пробы зашифрованы Fernet. Ключ шифрования находится **на этом же компьютере**: шифрование защищает от простого чтения базы, но не от пользователя с доступом к базе и ключу. Используйте права Windows и BitLocker. Не публикуйте каталог данных. Для резервной копии закройте приложение и скопируйте **весь каталог**, включая `vault.key`. Без ключа сохранённые секреты не восстановить.

PIN хранится как scrypt-хеш. Он закрывает доступ к интерфейсу, но не шифрует весь диск. После пяти неверных попыток — задержка на минуту. Кнопка блокировки доступна после установки PIN; мониторинг продолжается при блокировке. Забытого PIN приложение не отправляет и не показывает: восстановление требует работы с вашей локальной копией данных; не удаляйте её без резервной копии.

На один каталог данных разрешён один экземпляр приложения, чтобы не дублировать проверки и автоматические коммиты. В браузерном режиме не открывайте локальный API для сети: предусмотрен только loopback, защита Origin/Host и сессионная HttpOnly-cookie.

## Разработка и проверки в облачной среде

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python -m pytest -q
.venv/bin/python run.py --no-open --port 8765 --data-dir .local-data
```

Браузерный smoke-сценарий (Linux/Unix, Git и Chromium; Playwright установлен через `requirements-dev.txt`):

```bash
# Если Chromium не установлен, сначала: .venv/bin/python -m playwright install chromium
# CHROMIUM_PATH можно задать для собственного установленного браузера.
.venv/bin/python -m tests.ui_smoke
```

Сценарий поднимает временные HTTP/SSH-серверы и отдельный bare Git-репозиторий. Проверяет добавление/удаление проектов, реальный HTTP, SSH с закреплённым ключом, Git init/diff/commit/push, журнал, фильтры, PIN, экранирование HTML и адаптивность. Реальные хостинги и Telegram не затрагиваются. Скриншот — `test-results/dashboard.png`.

Тесты Git/SSH с Unix-shell пропускаются на Windows runner; API/PIN/HTTP-тесты запускаются. PHP-проба проверяется отдельно при наличии PHP: `DEVLIN_TEST_PHP=/path/to/php .venv/bin/python -m pytest tests/test_probe.py -q`.

Проверка настоящих Telegram/GitLab/SSH-проектов требует ваших подключений в интерфейсе. Доступы не вшиваются в код. В облачной среде внешние адреса могут требовать добавления в сетевые настройки; на Windows используются настройки сети вашего компьютера.
